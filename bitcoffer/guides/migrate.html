迁入与回滚：先确认门开着，再证明能还原

换密码管理器的风险有两层：一层是导入时少了几条，另一层是你以为备份能用、其实不能用。正确的顺序是：先确认应用不是只读态，再导出、导入、核对，最后用合成数据证明备份真能还原。

2026-11-09 更新 · 作者 cygnus（Bitcoffer 开发者）

零、动手前：先确认不是只读态

迁移的第一道门不是文件格式，是许可状态。Bitcoffer 对写入操作设了门禁，导入与恢复都在门禁里：状态不对时它们会被直接拒绝，界面表现不是「导入失败」，而是「不许写」。

状态导入恢复备份读取与导出拒绝码
已激活，或试用期未结束可以可以可以—
试用到期被拒被拒可以6002
订阅到期被拒被拒可以6005
已撤销被拒被拒可以6006
许可状态读取失败被拒被拒可以6003

这里有一条容易被讲错的纪律。「先备份再动手」并不足以保底：回滚本身也是写操作——删掉试点库是库级写、从备份恢复属于导入恢复组、把导入的条目丢进回收站是条目写——只读态下三条路一起失效。唯一仍被放行的是导出，所以顺序必须是：先确认不是只读态 → 再备份 → 再动手。

先记住一件事

只读态不等于不能用：查看、搜索、复制、导出加密备份都照常。被锁住的只有写——包括迁移和回滚。哪个状态下算只读，以 App 内许可页的显示为准 ⚠。

一、Bitcoffer 支持哪些来源

导入按文件格式处理，而不是按品牌。当前是五条路径：

来源文件格式说明
1Password.1pux官方导出格式，ZIP 归档，含附件。桌面端导出不含 passkey 字段；即便经其它路径带入，Bitcoffer 内 passkey 也不能创建、不能使用（降级：仅导入/查看/删除）。
1Password（旧版）OPVault 目录老版本 vault 格式，按目录整体选择；导入时要输 1Password 主密码；附件会跳过并计数。
Bitwarden未加密的 .json独立解析链，读密码 / 备注 / 自定义字段与 fido2Credentials；passkey 只有 ES256 行可导入，私钥为加密形态的行会跳过并在预检里逐条列出原因。迁入后的 passkey 是降级读面：只能导入、查看、删除，不能创建、不能使用。带密码保护的导出当前不支持。
Apple 密码（系统「密码」App）它导出的 CSV，放进指定目录菜单里叫「从 macOS 密码 App…」。选一个放置区目录并授权，之后在密码 App 里「文件」→「导出所有密码」存到该目录，Bitcoffer 自动检测、按库内去重、逐行可勾选。
通用CSV自身导出为 9 列；也能认 1Password 9 列、Chrome / Edge / Safari / 1Password 8 / Bitwarden / LastPass 的常见列名和中文表头。

.env 没有文件导入入口：它是「变量名 = 值」的形态，不是条目。要搬就按变量写进环境容器，用 CLI 的 set-env，值从终端隐藏输入，不落命令行、不进进程列表、不进日志。

其余厂商（Firefox、KeePassXC、Dashlane、NordPass 等）没有专门的样本与实测，不做承诺。它们的导出如果能落成上面任何一种格式，就按那种格式走。KeePass 的 KDBX 当前没有导入入口。

二、导出：先把明文拿到手，再谈导入

导出文件是明文的。落在哪里、什么时候删，是这次迁移里最容易被忽略的一步。

  • 导出到一个你结束后会删掉的位置，不要直接扔进 iCloud Drive 或「下载」目录长期留着。
  • 导出前确认文件大小合理：一个几千条的库导出成 3 KB，说明导出本身没成功。
  • 导出后先复制一份留档，迁移确认无误之前不删原件。
  • 1Password 用户：先想清楚要不要迁 passkey。要迁，就不要只带 1PUX——passkey 不随 1PUX 走，只随加密备份走；且迁入后仍不能创建、不能使用（仅导入/查看/删除）。
  • Bitcoffer 自己导出时：加密备份是整库归档；CSV 与 1PUX 都是明文、都要过「我已知晓风险」勾选加二次确认；1PUX 导出不包含回收站条目，也不包含 passkey。

三、导入：先弄清哪些路径能「只搬一部分」

入口有两处，同源：菜单「数据」→ 对应格式项，或工具栏「导入」菜单。快捷键只有两个——导入 CSV 是 ⌘I，导入 1Password (.1pux) 是 ⌘⇧I；Bitwarden 与 OPVault 没有快捷键。

「第一次只搬一小撮」这句话要看格式：四个导入向导（CSV / 1PUX / Bitwarden / OPVault）都没有条目勾选，预检页点下去就是全量；能逐行挑的只有「从 macOS 密码 App」那条放置区路径——它把每一行按新增 / 重复 / 冲突分类列出来，逐行可切换，按钮上的数字跟着变，重复项默认跳过、也可一键全部导入。所以想降低首次风险，实际可用的做法是：先迁一个条目少的库或项目，或者迁进一个专用试点库，而不是在向导里挑挑拣拣。

失败会怎么收拾，取决于格式的事务语义——这一点决定了中断后要不要重来：

格式事务语义中途失败会怎样
CSV / OPVault单事务，全或无一条都不落库，修好文件重来即可
1PUX / Bitwarden每条目独立事务已完成的条目保留；直接重试会重复新建，库里的条目数可能变成 1–2 倍
放置区（Apple 密码 CSV）单事务失败零落库

预检页各给什么，也值得提前知道：1PUX 给出总条目 / 可导入 / 附件数，并逐条列出未导入项；CSV 给出可导入条数、缺标题行与未识别列的清单；OPVault 的结构预检只校验目录结构与 profile 元数据，密码对不对要到导入时才见分晓，按钮写「开始导入」，所以它给不出条目数。

1Password 与 Bitwarden 各自导出向导里的菜单层级随对方版本变化，这里只承诺格式与文件名 ⚠。

四、校验：条目数要能对上，登录也要真登一次

导入完成后不核对数量，等于把「大概齐」当成迁移完成。三个数字应该能互相解释：

  • 源端的条目数；
  • 预检页的「可导入」与「未导入 N 条」；
  • 结果页写的「导入完成：新建 N 条条目」。

差多少、差在哪一类，要有答案。1PUX 的预检会单独列出三行条件计数——「回收站 N 条」「丢弃密码历史 N 条」「检测到 Passkey N 个」——出现就说明有东西没搬全，这是披露，不是报错。CSV 还有一层：认不出的列名不会丢数据，值会以「[未映射列 <列名>]」的形式并入备注，所以核对时顺手看一眼备注有没有异常长的一段。

数量对得上还不算完，再抽查 2–3 条，其中一条带 TOTP：

抽查动作操作
对密码选中条目按 ⏎ 或 ⌘⇧C 复制密码，粘到对应站点真登一次
对 TOTP按 ⌥⇧C 复制验证码，确认目标站点接受
对用户名 / 网址详情页逐字段比对，重点看带特殊字符的密码有没有被截断

1PUX 的结果页还会随机抽几条标题与类别供对照（抽样条数以当前版本为准 ⚠），但不会展示密码与正文，真正的核对还是要回主列表。

五、备份、恢复与回滚：先证明能还原

顺序很重要，别用真实凭据做第一次恢复测试。

  1. 建一个临时库（文件菜单「新建密码库…」），塞 3–5 条合成凭据（test-01 之类，密码随便但格式真实）。
  2. 做一次加密备份（⌘E，或菜单「数据」→「导出…」→ 加密备份），记下文件路径与时间。
  3. 把临时库删掉或移到别处，模拟最坏情况。
  4. 用备份恢复（设置 → 数据 →「从备份恢复…」，还没有库时首屏就有该入口），确认条目、字段、TOTP、附件都回来了。
  5. 只有第 4 步通过，再对真实库做第一次备份。

硬约束：Bitcoffer 的 passkey 是降级版——只能导入、查看、删除，不能创建、不能使用（见 FEATURES.zh.md 降级读面）。passkey 不随 1PUX 走，但会随加密备份走——这正是「备份不是可选项」的原因；迁完也不等于能拿它登录网站。备份文件本身是加密的，把它当密钥材料对待：放离线介质或你信任的加密存储，别和主密码放在一起。

真失败了，从三档里挑一档回滚

级别怎么做代价
库级（最干净）迁移前先建一个专用试点库，整个导入只在它里面做；不满意就 设置 → 数据 →「管理密码库…」删掉它。删除向导会先要求导出一份该库的加密备份。主库全程没被碰过；删库不可逆
备份级设置 → 数据 →「从备份恢复…」→ 选 .bitcoffer → 校验 → 恢复 → 用该库主密码解锁。回到备份那一刻，此后的改动丢失
条目级导入只会「新建」，不会覆盖库里已有条目，所以逐条「移到回收站」（⌘⌫）就等于撤销这次导入；回收站支持还原或彻底删除。删除是单条目操作，条数多会很慢

三档都是写操作，所以第零节那条前置检查不是客套：只读态下它们一起失效，届时唯一还能做的是导出。

六、迁完之后

  • 删掉导出文件，清空废纸篓。CSV 是明文，删除时机比 1PUX 更紧。
  • 在原管理器里保留一段时间，确认没有遗漏的自动填充项依赖它。Bitcoffer 没有浏览器扩展，日常取用靠复制粘贴与 ⌘⇧C / ⌘U / ⌥⇧C。
  • 把主密码与恢复码分开存放，恢复码只在你丢失主密码时使用。
  • 需要脚本或 AI 客户端取用凭据时，走明确的授权与注入路径，不要让它们读备份文件。
  • 哪天想搬回 1Password：导出按官方 1PUX v3 结构生成，但 1Password 没有对应类别的条目会被落成安全笔记——字段值与备注保留，类别语义丢失，导出报告不会提示。
